Tuần 2 + 4 giải thích siêu dễ

Dành cho người chưa biết Kong / MCP / Agent. Đọc như nghe bạn kể chuyện: làm gì → vì sao → gõ lệnh gì.

NHẢY TỚI 1. Câu chuyện 1 phút (hiểu cả bài) 2. 8 từ cần biết (ví dụ đời thường) 3. Luồng làm bài tuần 2 (từng bước) 4. Luồng làm bài tuần 4 (từng bước) 5. Tuần 2 và 4 nối nhau thế nào 6. Vì sao chọn cái này? Đánh giá thế nào? 7. Copy-paste chạy demo 8. Nộp gì cho mentor

1. Câu chuyện 1 phút

Bạn có một cửa hàng đồ chơi (Juice Shop) cố ý để lộ hàng — để tập bảo mật.

Bạn thuê robot trợ lý (AI Agent) giúp kiểm tra cửa hàng. Robot có thể làm việc rất nhanh — nếu cho nó chìa khóa ông chủ, một lần robot “điên” là phá cả shop.

Tuần 2: Bạn dựng cổng bảo vệ trước cửa hàng. Mỗi robot có thẻ riêng. Robot tuần tra chỉ được xem. Robot thử nghiệm mới được gửi/sửa — và không được vào phòng quản lý.

Tuần 4: Robot tuần tra đọc danh sách “chỗ nghi ngờ” từ máy quét tuần 1, rồi vẽ bản đồ các cửa / lối vào của shop (Attack Surface Map).

Nhớ 1 câu:
Tuần 2 = ai được làm gì (cổng + thẻ).
Tuần 4 = shop có những chỗ nào đáng xem (bản đồ).

2. 8 từ cần biết (ví dụ đời thường)

1. Juice Shop
App web giả lập để tập. Mở trình duyệt: http://localhost:3000. Giống “cửa hàng đồ chơi cố tình để lỗ” trong phòng lab.
2. Docker Compose
Nút bật phòng lab. Một lệnh là cả cửa hàng + cổng bảo vệ chạy. Bạn không cần cài app phức tạp bằng tay.
3. Kong (API Gateway)
= bảo vệ đứng trước cửa. Địa chỉ: http://localhost:8000.
Robot phải đi cửa này, không xô cửa sau (:3000) khi làm bài agent.
4. API key (thẻ nhân viên)
Chuỗi bí mật gắn vào request.
• Robot tuần tra: recon-key-demo
• Robot thử gửi dữ liệu: exploit-key-demo
5. GET và POST
• GET = xem / đọc (nhẹ).
• POST = gửi / tạo / đổi (nặng hơn, dễ gây hại).
Tuần tra chỉ được GET. Thử nghiệm mới được POST.
6. 401 / 403 / 429 (biển báo)
• 401 = không có thẻ / thẻ sai → “bạn là ai?”
• 403 = có thẻ nhưng việc này cấm → “không được vào”
• 429 = bấm chuông quá nhiều lần → “chậm lại”
7. MCP (tủ dụng cụ có nhãn)
Robot không tự lục tủ lung tung. Nó hỏi: “có dụng cụ gì?” rồi “cho mượn dụng cụ A”. Ví dụ dụng cụ: đọc kết quả quét, tìm tài liệu lỗ hổng.
8. Attack Surface Map (bản đồ cửa)
File JSON liệt kê các đường vào app (ví dụ trang tìm kiếm, đăng nhập…) kèm mức nguy hiểm. Tuần 4 làm ra cái này.

3. Luồng làm bài tuần 2 (làm theo thứ tự này)

Đừng nhảy bước. Làm xong bước 1 mới sang 2.

1
Bật phòng lab Mở Docker Desktop. Vào thư mục Project-Sentinel, chạy:
docker compose up -d
Đợi khoảng 1 phút. Kiểm tra:
  • Cửa hàng: mở trình duyệt http://localhost:3000 thấy Juice Shop
  • Cổng: http://localhost:8000 (chưa có thẻ sẽ bị chặn — đúng rồi)
2
Viết / hiểu luật trên cổng (Kong) File: kong/kong.yml. Ý đơn giản:
  • Không thẻ → cấm
  • Thẻ tuần tra → chỉ được xem (GET)
  • Thẻ thử nghiệm → được gửi (POST) nhưng không spam (giới hạn số lần/phút)
  • Đường /rest/admin (phòng quản lý) → cấm cả hai
Bạn không cần thuộc YAML. Chỉ cần giải thích được bảng quyền bên dưới.
3
Bảng quyền (học thuộc bảng này là đủ thuyết trình)
Ai Xem (GET) Gửi (POST) Vào /rest/admin
Không thẻ Không (401) Không Không
recon (tuần tra) Được Không (403) Không (403)
exploit (thử nghiệm) Được Được (có giới hạn) Không (403)
4
Chạy bài kiểm tra cổng (quan trọng nhất)
python scripts/test_kong_iam.py
Muốn đạt: hiện nhiều dòng PASS (7/7).

Ý nghĩa: bạn chứng minh chỗ bị chặn, không chỉ chỗ được vào.

python scripts/test_kong_rate_limit.py
Muốn thấy số 429 = cổng đã chặn spam.

Bật “tủ dụng cụ” MCP + gửi tin nhắn A2A Mở 2 cửa sổ terminal:

Bạn sẽ thấy: liệt kê dụng cụ → gọi đọc scan → từ chối tool lạ → ghi tin nhắn vào file.

Thử tool gửi request “ngoan”

4. Luồng làm bài tuần 4 (sau khi đã có cổng)

Tuần 4 không xây cổng nữa. Tuần 4 = robot tuần tra đọc sổ nghi ngờ rồi vẽ bản đồ.

Nguyên liệu đã có từ trước
  • Tuần 1: máy quét (Semgrep/ZAP) → lưu vào data-lake/vuln_data.db
  • Tuần 2: thẻ recon + MCP để đọc DB an toàn
1
Hiểu mục tiêu Đầu ra là file JSON kiểu danh sách:
  • Đường nào? (ví dụ /rest/products/search)
  • Nguy hiểm mức nào? (high / medium / low)
  • Vấn đề gì? (SQL injection, XSS…)
File này = bản đồ để tuần sau fuzz/test tiếp.
2
Cách robot làm (không thần thánh)
  1. Lấy danh sách lỗ hổng từ DB (qua MCP nếu đang bật)
  2. Mỗi dòng cố tìm “đường URL” liên quan
  3. Gom các lỗ cùng một đường lại
  4. Ghi ra file JSON
Đừng để AI bịa đường. Chỉ vẽ những gì có trong DB (hoặc baseline lab đã ghi rõ). Thiếu đường so với ghi chép tay là bình thường.
3
Chạy bản đơn giản trước (dễ hiểu)
python agents/mcp_server.py python agents/recon_skeleton.py
Ra file: data-lake/attack_surface_map.draft.json — mở bằng VS Code xem.
4
Chạy bản đầy đủ (nếu cần)
python agents/recon_agent.py
Ra: data-lake/attack_surface_map.json. Có thể kèm RAG (tìm tài liệu) và AI viết thêm chú thích — nhưng nền vẫn là DB.
5
So với bản đồ viết tay tuần 1 Đọc docs/notes/RECON_VS_MANUAL.md.

Người viết tay thường thấy nhiều đường hơn (vì xem UI/docs). Robot chỉ thấy những gì trong DB → overlap một phần là đúng và trung thực.

Tuần 4 xong khi nào?
✅ Có file map JSON
✅ Giải thích được: map lấy từ đâu (DB), không bịa
✅ Có so sánh với note tay (RECON_VS_MANUAL)
✅ Request (nếu có) đi qua Kong bằng thẻ recon

6. Vì sao chọn cái này? Dựa vào đâu? Đánh giá thế nào?

Phần này trả lời mentor: “Sao không làm cách khác?” và “Làm sao biết mình làm đúng / đủ điểm?”

6.1 Tiêu chí chọn công nghệ (trước khi chọn tên tool)

Mình không chọn “cái nghe oách”. Mình chọn theo 5 câu hỏi:

#Câu hỏiTrả lời của lab này
1 Mentor / PDF bắt buộc gì? Có Gateway + IAM cho agent + MCP/A2A (any) + map từ data
2 Có giải thích nổi trong 1 trang không? Phải căn bản — không IdP doanh nghiệp 20 file
3 Chạy được trên máy sinh viên không? Docker local, không cần GPU / cloud trả phí
4 Chứng minh được bằng số / lệnh không? 401, 403, 429, file JSON — không chỉ “em thấy ổn”
5 An toàn lab? Chỉ localhost, fail-closed (không chắc → chặn)

6.2 Vì sao chọn từng thứ?

Kong (không phải Nginx thuần / không tự viết proxy Python)
  • Vì sao: PDF gợi ý Kong/Nginx/gateway; Kong có sẵn plugin key-auth, ACL, rate-limit → đúng bài Agent IAM, ít code tự invent.
  • Không chọn Nginx thuần: làm ACL theo agent + rate-limit mất nhiều config hơn, khó demo “agent A vs B”.
  • Không chọn tự viết Flask proxy: dễ sai, không giống gateway thật, khó thuyết phục mentor.
  • Đánh giá chọn đúng khi: compose lên được, rule trong 1 file YAML, test PASS.
API key theo agent (không phải login user / JWT phức tạp)
  • Vì sao: Agent ≠ người dùng web. Cần identity máy đơn giản, gắn được vào header.
  • Không chọn OAuth đầy đủ: quá nặng cho lab 1 tuần, dễ “AI generate rồi không hiểu”.
  • Đánh giá: 2 key khác nhau → hành vi khác nhau (GET vs POST) là đủ chứng minh IAM.
Phân quyền theo METHOD + PATH (không chỉ “có key là vào hết”)
  • Vì sao: Mentor ví dụ rõ: được query users-ish nhưng không admin. Least privilege = giảm thiệt hại khi agent bị hijack.
  • Đánh giá: bảng deny xanh (403 path admin, 403 recon POST).
MCP (tủ tool có tên) thay vì mỗi agent tự mở SQLite
  • Vì sao: PDF/mentor gợi ý MCP/A2A; tool có tên = capability có kiểm soát (không có run_shell thì không gọi được).
  • Đánh giá: tools/list OK, get_scan_results OK, tool lạ bị từ chối.
A2A envelope + file jsonl
  • Vì sao: Sau này nhiều agent (Recon→Fuzz) cần tin nhắn có messageId để truy vết — không mất trong chat LLM.
  • Đánh giá: có dòng mới trong a2a_messages.jsonl.
Tuần 4: map từ DB trước, LLM sau (không để AI bịa bản đồ)
  • Vì sao: PDF muốn agent đọc kết quả quét; bịa endpoint = gian / eval giả.
  • Đánh giá: đổi dữ liệu trong DB → map đổi theo; so với note tay (overlap, không cần 100% giống).

6.3 Dựa trên cái gì để “chấm / tự đánh giá”?

Ba lớp — từ dễ đo → khó đo hơn:

Lớp Đo bằng gì? Đạt khi nào?
A. Bắt buộc (rubric) Đối chiếu đề mentor / PDF Có gateway, có IAM scoped, có MCP hoặc A2A, có map JSON
B. Kỹ thuật (bằng chứng) Script + mã HTTP + file output 401/403/429 đúng; log không lộ key; map sinh từ DB
C. Chất lượng tư duy Giải thích miệng / 1 trang MD Nói được vì sao chọn + failure mode (agent bị hijack thì sao)

Câu trả lời mẫu khi hỏi “sao chọn Kong + API key?”
“Em chọn Kong vì đề cho phép và có sẵn key-auth/ACL/rate-limit — đúng least privilege cho agent, chạy Docker local, cấu hình 1 file dễ giải thích. API key theo agent thay JWT user vì identity ở đây là máy robot, không phải phiên đăng nhập người. Em đánh giá bằng script: thiếu key 401, sai quyền 403, spam 429 — không đánh giá bằng cảm giác.”
